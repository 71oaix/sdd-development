# issue 前置自检（双向钢人）

> 可选步骤：只在命中触发条件时使用，不进入九步主循环。

## 定位

- 目的：在写 issue 之前，先厘清「真正要解决的问题」，避免把「嘴上问的」当成「真正想解决的」。
- 适用者：任何人对问题不够确定时；对 PM / 非技术决策者尤其有用——实现是黑盒，唯一能判断的是「要什么」。
- 产出落点：论证结果写入 issue 的「背景 / 目标」，不另开文档。

## 什么时候用（命中任一即可）

1. 一句话说不清「解决什么、为什么现在做、怎样算做对」
2. 做错代价大（涉及用户、数据、对外承诺、钱、方向）
3. 自己内心纠结，或「既要又要」
4. 同类任务之前返工过、效果不符合预期

## 什么时候不用

- 纯执行小任务：改文案、调样式、加字段、修明确的 bug
- 问题已经清楚、验收标准一句话能写出来

## Prompt 模板

````text
先别急着帮我写需求，也别默认我已经想清楚了。请先对下面这个需求做一次「双向钢人论证」：
1. 用最完整、最有力的方式，重述我真正想解决的问题（区分我嘴上说的和真正想要的）。
2. 分别给出「支持按我现在的想法做」和「反对这样做」的最强论证。
3. 找出双方真正的分歧，以及最可能改变结论的关键变量（如用户、成本、时间、影响范围、不可逆性）。
4. 只问我一个最关键的问题。等我回答后，再帮我明确需求目标、范围（含明确不做）和验收标准。

我的需求是：[粘贴需求]
````

## 使用步骤

1. 把需求粘进模板，让 AI 跑一遍双向钢人
2. 认真回答它问的那个关键问题（不跳过）
3. 把「重述后的真实问题 + 关键变量」抄进 issue 的背景 / 目标
4. 如果论证改变了你的想法，先改需求再写 issue

## 示例

需求：「给后台加一个搜索框。」

- 重述：真正要解决的是「用户找不到已有内容、重复提问」，搜索框只是方案之一。
- 反对最强论证：搜索功能开发与维护成本高；内容量不大时性价比低，整理目录 / 索引可能更便宜有效。
- 关键变量：内容量级与查找频率。
- 关键问题：「三个月后，你希望用户主要通过什么方式找到内容？搜索是最主要入口吗？」
- 回答后 issue 改写为：提升内容可发现性；MVP = 目录整理 + 站内搜索；明确不做：高级筛选、全文检索优化。
